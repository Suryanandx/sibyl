# Sibyl v0.4 — teams, workspaces and the enterprise edition

Status: **agreed** (2026-11-09): teams free, controls in Enterprise; Google and Microsoft connectors free, HubSpot and Salesforce in Enterprise; Enterprise licence modelled on the Elastic License 2.0 (final text to be approved by a lawyer). This document fixes the model before any code is written
so every part (chat, knowledge, skills, plugins, integrations, routines,
slides, usage) is built once, on the same foundation.

## 1. Editions and licensing (open core)

| | Sibyl (open source) | Sibyl Enterprise |
|---|---|---|
| Licence | MIT (unchanged) | **Sibyl Enterprise Licence** — source-available; production use needs a paid licence key |
| Where | everything outside `ee/` | `ee/` at the repo root (`ee/gateway`, `ee/web`, `ee/packages`) |
| Runs without a key | yes | no — enterprise modules stay off; the app works as open source |

Rules:

- **One-way dependency.** Open-source code never imports from `ee/`. Enterprise
  modules plug in through registries the core exposes (`features`,
  `permissions`, `auth providers`, `audit sinks`, `usage policies`). Deleting
  `ee/` must leave a working product. A CI check enforces this.
- **Licence key.** `SIBYL_LICENSE_KEY` is a signed token (Ed25519, verified
  offline against a public key in the binary): organisation, edition, seats,
  enabled features, expiry. No phone-home. Expired keys degrade to open source,
  never lock users out of their data.
- **Licence text.** `ee/LICENSE` uses an established source-available licence
  model (for example the Elastic License 2.0 pattern: free to read and modify,
  no offering as a managed service, no circumventing the key). **Have a lawyer
  approve the final text before release.**
- Code already published under MIT stays MIT. Only new enterprise code goes into `ee/`.

## 2. Tenancy

```
Instance (one deployment)
└── Organization            ← today's `ownerId` (default "owner")
    ├── Users + Memberships (org role)
    ├── Workspaces
    │   ├── Members (workspace role)
    │   ├── Chats, Knowledge bases, Skills, Plugins
    │   ├── Integrations (connections), Secrets
    │   ├── Routines, Slide spaces
    │   └── Settings: instructions, default models, budgets
    └── Org settings: SSO, policies, licence, audit (enterprise)
```

- `ownerId` keeps meaning **organization** everywhere, so existing data and code stay valid.
- Every record gains `workspaceId`; records without one belong to `default`.
- Records gain `createdBy` (user id) for attribution and "personal" visibility.
- Personal items: a chat is visible to its creator unless shared to the
  workspace; connections and secrets are **workspace** or **personal**.

## 3. Identity and sign-in

Open source:

- **First run:** create the owner account (email and password). `SIBYL_OWNER_TOKEN`
  stays for API and automation access, not for people.
- **Passwords:** hashed with `scrypt` from `node:crypto`. Sessions use an
  httpOnly SameSite=Lax cookie, plus a WebSocket ticket exchanged from the cookie.
- **Invitations:** one-time invite links (copy link), or email when SMTP is
  configured. An invite carries the workspace and role.
- Password reset by link.

Enterprise:

- SSO (OIDC and SAML), SCIM provisioning, enforced SSO and domain claim.
- Session policies: lifetime, IP allowlist, MFA requirement.

## 4. Permissions (RBAC)

One catalogue of permissions, grouped by product area. Every WebSocket
handler, HTTP route and tool call goes through a single
`authorize(principal, permission, resource)`. The UI hides what you can't
do, but the server decides.

| Area | Permissions |
|---|---|
| Chat | `chat.use`, `chat.share`, `chat.view_all` |
| Knowledge | `knowledge.view`, `knowledge.edit`, `knowledge.manage` |
| Skills & plugins | `skills.use`, `skills.edit`, `plugins.install` |
| Integrations | `integrations.use`, `integrations.connect_personal`, `integrations.connect_shared` |
| Connections (MCP) | `mcp.manage` |
| Secrets | `secrets.use`, `secrets.manage` |
| Routines | `routines.use`, `routines.manage` |
| Slides | `slides.use`, `slides.manage` |
| Models & usage | `models.choose`, `usage.view`, `budgets.manage` |
| Workspace | `workspace.settings`, `members.invite`, `members.manage` |
| Organization | `org.settings`, `org.billing`, `audit.view` (enterprise) |

Built-in roles (open source): **Owner**, **Admin**, **Member**, **Viewer**,
at organization and workspace level.

Enterprise:

- Custom roles.
- Per-resource grants (for example, only Sales can use the Salesforce connection).
- Policies:
  - write actions that always need an admin's approval;
  - model allowlists;
  - blocked tools;
  - data retention.

**Approvals:** write actions still need the acting user's approval card.
Policies can add a second approver.

## 5. Usage controls

- **Open source:** organization and workspace budgets (daily and monthly), with
  usage by workspace and feature. The economy switch at 85% stays as it is.
- **Enterprise:** per-user and per-role budgets; model and cost caps per
  request; rate limits; alerts by email or webhook; chargeback reports by
  workspace and user; CSV export.

## 6. Integrations (native connectors)

One connector framework with a short, curated list. Each connector is code
plus a manifest. No prompts are bundled: it only exposes actions that the brain
can call.

```ts
interface ConnectorDefinition {
  id: "google" | "microsoft" | "hubspot" | "salesforce";
  auth: { kind: "oauth2"; scopes: string[] } | { kind: "apiKey" };
  actions: ToolDefinition[]; // read actions run; write actions need approval
}
```

- **Google Workspace:**
  - Gmail: search, read, draft, send;
  - Calendar: list, create, update;
  - Drive: search, read;
  - Docs: read, create, append;
  - Sheets: read, append, update.
- **Microsoft 365:**
  - Outlook mail: search, read, draft, send;
  - Calendar;
  - OneDrive: search, read;
  - Excel: read, update;
  - Teams: post a message to a channel.
- **HubSpot** *(Enterprise)*: contacts, companies, deals (search, read, create, update), notes.
- **Salesforce** *(Enterprise)*: SOQL query (read), records (get, create, update), and logging an activity.
- **Authentication:** OAuth uses the organization's own app credentials (client ID and secret, saved as secrets). The callback lives on the gateway. Tokens stay encrypted in the secrets vault and refresh automatically.
- **Connection scope:** a connection can be personal or shared with a workspace.
- **MCP:** stays as **Advanced → Custom connector** for anything else.

## 7. Workspace features

- **Knowledge bases:**
  - Content: uploads, web pages and pasted text, split into labelled chunks.
  - Search: SQLite FTS5 keyword search out of the box; embeddings optional.
  - Tool: `search_knowledge` with citations.
  - Scope: a workspace can auto-attach bases to every chat.
- **Skills:** named instruction packs ("how we write release notes").
  - The brain sees only each skill's name and description, and loads the full body with `use_skill` when relevant.
  - Create in the app, or import a `SKILL.md` folder or zip.
- **Plugins:** `sibyl-plugin.json` bundles skills, MCP servers, required secrets
  and routine templates.
  - Install from the catalog, a URL or git. Missing secrets are asked for with the secure box.
  - Enable or disable as one unit.
- **Uploads:** stay attached to messages, and can be saved into a knowledge base in one click.

## 7a. Agents (your own assistants, with their own look)

An **agent** is a named setup people can create and share in a workspace, built
from the same parts as everything else. There are no separate agent runtimes.

- **Identity:** name, short description, an **avatar**, an optional voice.
- **Behaviour:** instructions, a model preset, and the skills, knowledge bases,
  integrations and tools it may use. Writes still need approval.
- **Use it:**
  - pick it in the composer ("Ask Research Dot…"), or `@mention` it in a chat;
  - routines can run as an agent;
  - the brain can hand a sub-task to an agent ("ask Sales Buddy to draft the follow-up").
- **Avatars ("dots"):** Sibyl's own generator. Deterministic, cute characters
  (dots, blobs, small pets) built from shapes in SVG, with no image-model cost.
  - **Customise:** body shape, colour palette from the Sibyl tokens, eyes, mouth, accessory, and a seed with a "shuffle" button.
  - **Moods:** the avatar animates through the same states as the Sibyl emblem: idle, listening, thinking, speaking.
  - **Optional upload:** your own image instead.
- **Templates:** a few starter agents (Research, Writer, Sales follow-up,
  Meeting prep) that show what a good setup looks like.
- **Permissions:** `agents.use`, `agents.create`, `agents.share`.
- **Enterprise:** per-agent budgets and an approval policy.

### 7b. Agents that learn, work and watch

**Decision:** self-learning is built into Sibyl's own brain and uses the same
skills, memory, tools, approvals, budgets and permissions as everything else.
It follows the patterns popularised by Hermes Agent (Nous Research, MIT): skills
the agent writes from experience, curated memory, and search over past sessions.
We don't run a second agent runtime next to Sibyl.

- **Learning loop:**
  - After a task with several steps, the agent reflects on it. When it found a
    better way, it proposes a new skill or an edit to one.
  - Skills are Markdown, versioned, and show who or what wrote them.
  - Each agent has a setting: *ask me first* (the default) or *learn automatically*.
  - Learned skills can be reviewed and rolled back, so behaviour never drifts silently.
- **Memory per agent:** a short, curated profile (what it knows about the user and
  team) plus search over the agent's past conversations and runs (FTS5).
- **Its own computer:** an optional sandbox for each agent, a container with a
  real browser (Playwright) and a file area. A desktop view is a later addition.
  - **Isolation:** no host access, network rules, CPU and time limits.
  - **Watching:** people can watch the browser live, or as a recording afterwards.
  - **Safeguards:** logging in, buying or sending from the browser is a write
    action, so it needs approval.
- **Where it lives:**
  - inside Sibyl (chat, `@mention`, the Agents screen);
  - in **Slack** and **Microsoft Teams**: it joins channels and answers threads,
    through the same connector framework (Teams with Microsoft 365, Slack as its
    own connector).
- **Monitors ("keep an eye on it"):**
  - **Watch:** sources such as Gmail and Outlook, Calendar, Drive and OneDrive,
    HubSpot and Salesforce, RSS or web pages, and knowledge bases. Watching uses
    webhooks where the source offers them, otherwise polling on a schedule.
  - **Condition:** a plain-language test such as "a deal over $50k moves to
    Negotiation", evaluated cheaply (filters first, the model only on candidates).
  - **Action:** notify in the inbox, by email, or in Slack/Teams, or start a task.
    Write actions still need approval.
  - **Cost:** every monitor has a budget and shows what it has cost.
- **Delivery:** agents with identity, avatars, skills, memory and monitors
  come in wave B. Agent computers and the Slack/Teams presence come in wave C.
  - **Enterprise extras:** per-agent budgets, policies, and audit of agent
    actions, including browser recordings.

### 7c. Access and autonomy (the agent settings that matter most)

Agents are the centre of Sibyl: teammates people build themselves.

- **Access:**
  - **Everything I can use** (default): the agent can use every connector,
    knowledge base, skill and tool its creator may use in the workspace, now and
    as they add more. It can never exceed the creator's permissions.
  - **Controlled:** pick exactly which connectors (and which of their actions),
    knowledge bases, skills, tools and secrets it may use.
- **Autonomy** (how it acts):
  - **Ask first:** every write action needs approval. This is the default for new agents.
  - **Act, then tell me:** writes run within the agent's budget and are
    reported in the inbox, with undo where the source allows it.
  - **Fully autonomous:** runs on its own (monitors, routines, channels)
    within budget and policy. High-risk actions (send money, delete, share
    externally) always ask.
- **Voice:** each agent has its own voice and personality. You can talk to it live,
  just like Sibyl, and it can join a Slack or Teams call later.
- **Learning:** "ask me first" or "learn automatically". Every learned skill and
  memory is visible, editable and can be rolled back.
- **Budget:** per agent, per day and month. Agents pause cleanly at the cap.

### 7d. Realtime layer: LiveKit (wave C)

The self-hosted, Apache-2.0 LiveKit stack becomes Sibyl's optional media layer.
The current WebSocket voice path stays as the zero-setup default, so a single
OpenRouter key still runs everything.

| Part | What it gives Sibyl |
|---|---|
| **livekit (server)** | WebRTC rooms: lower and steadier latency, echo cancellation, jitter buffering, mobile networks; several people and agents in one call |
| **agents (`@livekit/agents`, Node)** | Sibyl's voice brain runs as a LiveKit agent *in TypeScript*, reusing our brain, hedging, metering, approvals and OpenRouter models. Agents join rooms with their own voice |
| **SIP (in the server stack)** | Agents can answer and place phone calls (support lines, reminders, call-backs) |
| **egress** | Record calls and **agent computer** sessions (watch later; Enterprise audit recordings) |
| **ingress** | Bring a live stream (RTMP/WHIP/URL) into a room, so an agent can listen to a meeting or webinar and take notes |

Notes:

- LiveKit's **turn-detector model** weights are under a separate LiveKit Model
  License (not Apache-2.0). It is opt-in after licence review; our own VAD and
  turn logic stay the default.
- Compose profile `realtime` adds `livekit`, `egress` and `ingress`. The web app
  uses `livekit-client` when the gateway advertises a LiveKit URL, and falls
  back to WebSocket otherwise.
- Costs: media is self-hosted (no per-minute fees). Model spend stays metered as today.

## 8. App structure (screens vs dialogs)

- **Screens** (full page in the app frame, own address):
  - Chat `/c/:id`
  - Slides `/library/slides`
  - Knowledge `/knowledge`
  - Agents `/agents`
  - Skills & plugins `/skills`
  - Integrations `/integrations`
  - Routines `/routines`
  - Inbox `/inbox`
  - Settings `/settings/:section` — sections: workspace, members, models, voice, memory, usage, secrets
  - Admin `/admin/:section` — org, users, roles, policies, audit, licence (enterprise)
- **Dialogs**, only for short tasks: confirmations, approval details, the secure key box, the quick model menu, invite someone.
- **Workspace switcher** at the top of the rail. Everything shown is scoped to the current workspace.

## 9. Audit (enterprise)

An append-only audit log of:

- sign-ins;
- role changes;
- connection grants;
- secret access by name (never values);
- approvals;
- tool calls with write effects;
- exports.

It can be exported, or streamed to a webhook or SIEM.

## 10. Migration from v0.3

1. Organization `owner` and workspace `default` are created automatically.
2. On first start, the owner sets an email and password. The existing owner token keeps working for the API.
3. Existing records keep working because a missing `workspaceId` means `default`.

| Wave | Parallel work |

| A — foundation | users, sessions, invites, memberships, `authorize()`; licence + `ee/` registry; app shell (screens, workspace switcher, settings/admin layout) |

## Appendix A — Permission enforcement (wave A, as built)

Every entry point checks `authorize(principal, permission, { workspaceId })`
from `packages/core/src/permissions.ts`. Principals: a signed-in **user**
(cookie `sibyl_session`), the **token** principal (`SIBYL_OWNER_TOKEN`, org
owner), or **local** (no accounts yet and no owner token: org owner, so
existing single-owner installs behave as before). The workspace is the
connection's current workspace (WebSocket, switched with `session.workspace`)
or `x-sibyl-workspace` / `?workspaceId=` (HTTP; default `default`).

Built-in roles: Viewer ⊂ Member ⊂ Admin = Owner (workspace level); org
Owner/Admin carry their role into every workspace; `org.*`/`audit.view` come
from the org role only. Owner-only actions beyond the permission sets: delete
a workspace; grant or change the owner role. Nobody grants a role above their
own; the last owner of a workspace can't be removed or demoted. One permission
was added to the §4 catalogue: `tools.write` (run write tools and decide their
approvals; Viewer lacks it).

| Entry point | Permission |
|---|---|
| WS upgrade | signed in (cookie from an allowed origin, `?token=`, or local mode) |
| WS `session.start`, `playback.ack`, `interrupt` | — (own session) |
| WS `session.workspace` | any role in the target workspace |
| WS `session.update` | model fields (`voiceModel`, `llmModel`, `sttModel`, `ttsModel`): `models.choose`; voice/speak/genUi: — |
| WS `user.text`, `audio.chunk`, `vad.speech_start`, `vad.speech_end` | `chat.use` |
| WS `conversations.request`, `conversation.open`, `conversation.delete` | `chat.use`; only chats in the workspace, created by the caller unless `chat.view_all` (pre-v0.4 chats: `chat.view_all`) |
| WS `approval.decision` (chat and routine approvals) | `tools.write` |
| WS `usage.request` | `usage.view` (silently ignored otherwise) |
| WS `connections.request` | `chat.use` |
| WS `connections.tool_toggle`, `server_toggle`, `server_save`, `server_remove`, `server_reconnect`, `server_test` | `mcp.manage` |
| WS `routines.context`, `routines.request`, `inbox.request` | `routines.use` |
| WS `routine.update`, `routine.run_now`, `routine.delete` | `routines.manage` |
| WS `secret.provide`, `secret.cancel`, `secrets.list` | `secrets.use` |
| WS `secret.update`, `secret.delete` | `secrets.manage` |
| WS any other / future type | `chat.use` (fallback in `identity/ws.ts`) |
| Brain tool calls (typed chat, deep work, live voice) | write tools: `tools.write` — not offered to the model and refused at run time; principal + workspace passed in `ToolContext` |
| `GET /api/uploads/:id`, `POST /api/uploads` | `chat.use` |
| `GET /api/memory` | `chat.use` |
| `POST/PATCH/DELETE /api/memory[/:id]` | `knowledge.edit` |
| `PUT /api/memory/settings` | `workspace.settings` |
| `GET /api/slides/*` (status, sources, templates, decks, downloads, thumbnails, spaces) | `slides.use` |
| `POST/PATCH/DELETE /api/slides/*` (generate, spaces) | `slides.manage` |
| `GET /api/auth/me`, `POST /api/auth/login`, `/logout` | — |
| `POST /api/auth/setup` | only while there are no accounts; needs the owner token when `SIBYL_OWNER_TOKEN` is set |
| `GET /api/workspaces` | signed in (lists workspaces the caller can open) |
| `POST /api/workspaces` | `org.settings` |
| `PATCH /api/workspaces/:id` | `workspace.settings` |
| `DELETE /api/workspaces/:id` | workspace owner; never `default` |
| `GET /api/workspaces/:id/members` | any role in the workspace |
| `PATCH /api/workspaces/:id/members/:userId` | `members.manage` (+ not above own role; last owner kept) |
| `DELETE /api/workspaces/:id/members/:userId` | `members.manage`, or yourself; `POST …/leave` yourself |
| `GET /api/invites?workspaceId=`, `POST /api/invites`, `DELETE /api/invites/:id` | `members.invite` (+ role not above own) |
| `GET /api/invites/:token`, `POST /api/invites/:token/accept` | — (the one-time token) |
| `GET /healthz` | — |

Usage, budgets and the economy switch are still organization-wide (wave B
makes them per workspace); routines, approvals, secrets and connections are
organization-wide records checked against the caller's role in the current
workspace.

Migration from v0.3 (§10): schema migration 3 adds `users`, `memberships`,
`invites`, `sessions` and `conversations.created_by`; nothing else changes.
With no accounts the gateway stays in single-owner local mode (or owner-token
mode). The first `/setup` creates the owner (org owner + owner of `default`,
which is created if missing, named "Personal"); from then on people sign in,
and existing chats (no `createdBy`) are visible to owners and admins.
